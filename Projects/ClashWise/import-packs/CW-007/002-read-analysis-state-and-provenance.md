## Read the row state before the values

@screen: Compare analysed with rule, analysed without a rule, and not-yet-analysed icons.

The icon beside a title tells you whether the clash was analysed and whether a rule matched.

A completed analysed row with a matched rule shows a success state. A warning means analysis completed but no suitable rule was found. An unanalysed row remains visibly different. During a run, progress indicators separate work in flight from a genuine missing result.

If a sparkle appears beside the matched rule, one or both element classifications were inferred rather than read directly from a captured class value. That is a useful review cue, not an automatic error.

## Follow the matched rule

@action: Open clash number twelve's Matched Rule link in a second tab and highlight the two classes and configured defaults.

The matched rule is the provenance for the recommendation. Check the element-class pairing first. Then inspect its configured priority, status, responsible contact, tolerance, colour, and any tags.

Tolerance belongs to the rule logic and uses the clash set's source units. Tags can be applied when rule-tag generation and analysis are configured to do so. The grid's main recommendation columns focus on priority, status, and responsible contact, while the linked rule gives you the wider context.

If the classes are wrong, fix property mapping or class extraction. If the classes are right but the recommendation is wrong for the project, change the matrix rule. Correcting the shared cause is more scalable than repairing hundreds of clashes one by one.
