## Review class keys before generation

@action: Sort through the scanned Riverside inventory, compare class and discipline keys, counts, and raw-variant totals.

Inventory shows the classes the matrix can actually use. Every key is selected initially, but selection is deliberate.

Keep the architecture, structure, mechanical, electrical, and plumbing classes that belong in the coordination strategy. Exclude annotations, temporary proxies, container objects, and any near-unique value that slipped through the property choice.

Element count helps reveal mistakes. A class that appears once may be valid; hundreds of almost identical one-item classes usually signal that the property is too detailed. Raw variants show when several exact source values consolidate into one matrix key while remaining available for precise search creation.

The number of matrix rules grows with the selected class pairings. ClashWise applies its existing rule-limit validation before generation. Reducing noise here produces a matrix that is faster to review and clearer to maintain.

## Create the durable setup

@action: Continue to Create and choose Create setup and matrix.

Creating saves the federation sources, classification mapping, selected inventory, semantic revision, and model-profile origin. It then sends the selected class keys through the existing matrix-generation pipeline.

The setup owns the default-matrix relationship. The matrix remains a normal ClashWise matrix with its normal edit permissions. Future clash sets bound to this profile can inherit the current default without duplicating the rulebook.

Wait for the cloud status to confirm the setup and matrix were created. A failed generation is not a partly usable matrix. Keep the window open, record the exact message, and retry only after correcting the source or class selection that caused the problem.
