## Compare both elements

@action: Open the Element A and Element B cards and point out category, source, type, level, and identifiers.

A clash is a relationship between two elements. Review both sides before deciding who owns it.

The element cards use the published mappings and can show whether a category was inferred. Confirm that the source files, categories, types, levels, and IDs fit the issue you see in the viewpoint.

If a value is wrong across many clashes, return to Property Mapping and republish or update. Do not repair systemic source data with dozens of manual comments.

## Use all properties and spatial context

@screen: Search the All properties section, copy one value, create a filter from another, and show the geometry or location section.

All properties contains the wider Navisworks property catalogue captured at publish time. Search for the asset or system value that identifies this equipment run. You can copy a value or create a grid filter directly from it to find related clashes.

Location combines published grid data with vendor-neutral spatial assignment when that evidence is available. A clash may show building, level, primary room or space, overlapping space identities, assignment source, confidence, and the normalized anchor used to place it.

The exact Navisworks clash centre is the preferred anchor. A viewpoint anchor or bounding-box evidence can be used when the centre is unavailable. ClashWise never guesses the nearest room merely to fill a label.

Room and level assignment requires a ready, aligned IFC context model designated for Rooms and spaces. Unaligned or geometry-only context can still render without claiming room containment. Older sets may need republishing with the current plugin before exact clash centres and the newer spatial fields are available.
