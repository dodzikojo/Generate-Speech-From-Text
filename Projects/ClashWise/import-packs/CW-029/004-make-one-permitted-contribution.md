## Show permitted controls

@action: As the guest, mark one clash reviewed, change status or priority, add a comment, and flag it for discussion.

A fixed-lane guest can change status and priority, mark reviewed, flag, comment, and capture markup. They can navigate, point, and drive the room.

They cannot change responsible contact, switch to another lane, access reports, exports, organisation settings, AI, API, other sessions, or the rest of the set.

Do not probe destructive boundaries in a training take. Point to unavailable controls and explain the scope.

## Verify provenance as host

@screen: Return to the host activity feed and show the guest's name on the review, field change, and comment.

Guest contributions enter the same session and clash history as member work, with the guest identity attached. Their access can end while their valid work remains.

The roster and later report distinguish that they joined live.

## Create a pass only from an eligible lane

Guest access is tied to a responsible-contact lane. The contact and email come from the assigned coordination data; the host does not create a generic guest room for any arbitrary address.

Before generating the pass, confirm the lane contains only work appropriate for that external person. Correct mistaken responsibility in the set instead of using the guest link as a workaround.

Treat the URL as a credential. Deliver it through the intended channel and avoid showing it in a recording, support ticket, or public meeting chat.

## Review the guest boundary

@action: Open the prepared pass in a clean signed-out browser and hold on Your access brief.

The access brief is generated by the product from the lane and current permission boundary. It is not a freeform briefing written by the host.

Read the visible capabilities before demonstrating a contribution. The guest should see the assigned lane, not the full project. Save one permitted comment or session contribution, then return to the member view and confirm its provenance.

Revoke the pass and reload the signed-out page. Access should fail while the valid contribution remains in the session history. That combination—closed credential, preserved audit—is the success condition.
